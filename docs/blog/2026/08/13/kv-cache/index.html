The KV Cache

The buffer that makes generation affordable is also the reason serving a language model is hard.

Published

13 August 2026

Read time

9 min read

Tags

Foundations for LLM

A language model has no memory of what it has said. Writing a hundred tokens means a hundred calls, each on a sequence one token longer, each rebuilding its view of the past. The KV cache stops the rebuilding, and most of what is hard about serving a model follows from this one buffer.

The Only Thing in a Transformer That Remembers

Everything else is shared and static: one set of weights, read by every request. The cache belongs to one sequence and usually dies with the reply.

Figure 1. One attention layer at decode step $t$. Of the three projections of the arriving token, only the key and value are appended; the query then attends over every cached row.

1. A Trick Nobody Published, and the Bill That Came Later

The first box has no citation because nobody claimed it as a contribution. Shazeer's 2019 paper prints the algorithm, but as setup; what it adds is the diagnosis, blaming "the memory-bandwidth cost of repeatedly loading the large “keys” and “values” tensors".

2. Two Tensors, One Row Longer Every Step

For a multi-head or grouped-query layer, the cache is two tensors per layer per sequence:

$$ K_{\text{cache}},\; V_{\text{cache}} \in \mathbb{R}^{\,n_{kv} \times t \times d_h}, $$

with $n_{kv}$ key-value heads, $t$ tokens so far, and $d_h$ the head dimension.

The queries are not cached, and that asymmetry is the whole idea. Attention is a question the present asks of the past: $q_t$ against $k_1 \dots k_t$. A past key is consulted at every future step; a past query was asked once and is never asked again.

Two regimes follow. Prefill takes the whole prompt at once, filling the cache in one matrix–matrix pass that saturates the hardware. Decode takes one token and reads the whole cache back, moving far more bytes per sequence than it performs operations.

Four tokens by hand

Figure 2. Four tokens, two heads, $d_h = 4$, a prompt of two. Each step adds one new row per cache; earlier rows are reused untouched. The bars are softmax weights, computed from the vectors beside them.

Why any of this is allowed

Under a causal mask, $k_i$ and $v_i$ depend on token $i$ and its predecessors alone, so appending a token cannot change a row already written. Test the received rule against that — the KV cache only works in decoders. Nearly right, wrong reason. An encoder caches nothing because every representation depends on the whole sequence; cross-attention is cached, and it is bidirectional, cacheable because the encoder's output is finished rather than masked. A row is cacheable when nothing arriving later can change it, and causality is the usual guarantee of that, not the only one.

Figure 3. Append one token and ask what survives. Masked, existing rows stay valid; unmasked, every row must be recomputed.

How big it gets

For $L$ layers at $p$ bytes a number,

$$ \text{bytes} \;=\; 2 \, L \, n_{kv} \, d_h \, t \, p . $$

The 2 keeps both $K$ and $V$. Llama 3 8B, with $L = 32$, $n_{kv} = 8$, $d_h = 128$, spends 128 KiB on every token in fp16; Llama 3 70B spends 320 KiB, so the 128k context of Llama 3.1 is 40 GiB of cache for one conversation.

3. One Room per Guest, and the Weights Everyone Shares

The cache is not merely large, it is large per sequence, which batching amortizes only when sequences happen to share a prefix. Shazeer gives the ratio of memory access to arithmetic during decoding as

$$ \Theta\!\left(\frac{n}{d} + \frac{1}{b}\right), $$

with $n$ the sequence length, $d$ the width, $b$ the batch, and the estimate assuming $n \le d$ — long contexts only make the term worse. Near 1, the hardware moves a byte per operation, on a machine built for three hundred operations a byte. The $1/b$ term is friendly — raise the batch and the weights are read once for many sequences. The $n/d$ term is not, because every sequence drags its own cache along.

Figure 4. A Llama 3 8B-shaped model on one H100 at peak bandwidth and peak dense FLOP/s — an upper bound on a machine nobody has. The bar splits each step's bytes into weights, read once per batch, and cache, read once per sequence. Nothing in range is compute-bound.

Shrinking the cache was one answer — a shared key-value head, then grouped ones, which deserve their own post. But a second failure survives any shrinking. The kernels of the day took the cache as one dense tensor, and nobody knows how long a request runs, so systems reserved each its maximum length. What that costs on real traffic is why vLLM exists.

Figure 5. Four requests growing in one strip of memory. Solid cells hold keys and values; pale ones are reserved and empty.
Figure 6. Reproduced from Kwon et al. (2023), Figure 2, recoloured into this site's palette. Each bar is all of a system's KV cache memory; the bottom band alone holds token states — 20.4% to 38.2% before paging, 96.3% after. No tensor got smaller.

One last cost differs in kind. Paging and batching leave a given model's output untouched; evicting old tokens or storing them in four bits does not. Sharing key-value heads is a third thing — not an approximation of a model but a different model, trained to be one.

4. The Same Answer to Fifteen Decimal Places

Decoding 320 tokens through one attention layer, $d = 768$ in 12 heads, each step done both ways, the largest disagreement is $2.2 \times 10^{-15}$ — float64 noise. The cache is algebraically exact: it changes no term in the definition of attention. Two bf16 kernels will still disagree in the last bits, but that is floating point, not the cache.

The saving has the shape the arithmetic claims. A cached step projects one token and attends over $t$ rows: $8d^2 + 4td$. A recomputing step projects $t$ tokens and attends over $t \times t$: $8td^2 + 4t^2d$. Every term of the second carries a factor $t$ the first does not, so the ratio is exactly $t$ — against this dense baseline; one exploiting the mask tends toward $t/2$.

Figure 7. Measured, from figures/kvcache.py. In (a) the no-cache step lands on its predicted curve; the with-cache step is flat and far above its own. (b) is the bill — wall-clock on one laptop, so expect the 11$\times$ to move.

Panel (a) is the interesting failure: at one token per step, arithmetic is not what is being paid for — section 3 arriving early, unarranged, on a laptop.

5. Chat This Over With Friends

A language model remembers nothing between words. Every token it writes is a fresh call on the whole conversation so far, and if it truly started over each time, the cost of a reply would grow with the square of its length. The KV cache is the fix, and it is embarrassingly simple: each token's key and value are computed once and kept, because a causal model can never go back and change them. Notice what is not kept — the queries. A past token's key is consulted forever; its question was asked once and never again. In a 70B model each token costs 320 KiB of it, so a long conversation quietly accumulates 40 GiB, for one user.

The version people repeat is that the KV cache is a decoder-only trick. Close, but the reason is not the name of the block: encoder–decoder models cache cross-attention keys quite happily, bidirectional though that is, while an encoder caches nothing because appending a word rewrites every representation it had. A row is keepable when nothing arriving later can change it. The fair objection is that calling the cache the bottleneck overstates it — at a large batch and a short context the weights still dominate — so the honest claim is narrower: it binds at long context, which is where everyone now operates. What is unsettled is the next move, since evicting tokens and four-bit storage both change what the model computes, and stop being free in the way paging was.
