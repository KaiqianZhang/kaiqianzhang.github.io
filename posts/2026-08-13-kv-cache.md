A language model has no memory of what it has said. Writing a hundred tokens
means a hundred calls, each on a sequence one token longer, each rebuilding
its view of the past. The **KV cache** stops the rebuilding, and most of what
is hard about serving a model follows from this one buffer.

## The Only Thing in a Transformer That Remembers

Everything else is shared and static: one set of weights, read by every
request. The cache belongs to one sequence and usually dies with the reply.

## 2. Two Tensors, One Row Longer Every Step

For a multi-head or grouped-query layer, the cache is two tensors per layer
per sequence:

$$
K_{\text{cache}},\; V_{\text{cache}} \in \mathbb{R}^{\,n_{kv} \times t \times d_h},
$$

with $n_{kv}$ key-value heads, $t$ tokens so far, and $d_h$ the head
dimension.

The **queries are not cached**, and that asymmetry is the whole idea.
Attention is a question the *present* asks of the *past*: $q_t$ against $k_1
\dots k_t$. A past key is consulted at every future step; a past query was
asked once and is never asked again.

Two regimes follow. **Prefill** takes the whole prompt at once, filling the
cache in one matrix–matrix pass that saturates the hardware. **Decode** takes
one token and reads the whole cache back, moving far more bytes per sequence
than it performs operations.

### Why any of this is allowed

Under a causal mask, $k_i$ and $v_i$ depend on token $i$ and its predecessors
alone, so appending a token cannot change a row already written. Test the
received rule against that — *the KV cache only works in decoders*. Nearly
right, wrong reason. An encoder caches nothing because every representation
depends on the whole sequence; cross-attention **is** cached, and it is
bidirectional, cacheable because the encoder's output is finished rather than
masked. A row is cacheable when nothing arriving later can change it, and
causality is the usual guarantee of that, not the only one.

### How big it gets

For $L$ layers at $p$ bytes a number,

$$
\text{bytes} \;=\; 2 \, L \, n_{kv} \, d_h \, t \, p .
$$

The 2 keeps both $K$ and $V$. Llama 3 8B, with $L = 32$, $n_{kv} = 8$, $d_h =
128$, spends **128 KiB on every token** in fp16; Llama 3 70B spends 320 KiB,
so the 128k context of Llama 3.1 is 40 GiB of cache for one conversation.

## 3. One Room per Guest, and the Weights Everyone Shares

The cache is not merely large, it is large *per sequence*, which batching
amortizes only when sequences happen to share a prefix. Shazeer gives the ratio of memory access to arithmetic
during decoding as

$$
\Theta\!\left(\frac{n}{d} + \frac{1}{b}\right),
$$

with $n$ the sequence length, $d$ the width, $b$ the batch, and the estimate
assuming $n \le d$ — long contexts only make the term worse. Near 1, the
hardware moves a byte per operation, on a machine built for three hundred
operations a byte. The $1/b$ term is friendly — raise the batch and the weights
are read once for many sequences. The $n/d$ term is not, because every
sequence drags its own cache along.

(function () {
  var scene = document.getElementById('rl-scene'),
      bR = document.getElementById('rl-b'), lR = document.getElementById('rl-l'),
      kR = document.getElementById('rl-k'), note = document.getElementById('rl-note'),
      bOut = document.getElementById('rl-b-out'), lOut = document.getElementById('rl-l-out'),
      kOut = document.getElementById('rl-k-out');
  var LAYERS = 32, DH = 128, DMODEL = 4096, BYTES = 2;
  // Llama 3 8B is 8.03B parameters at 8 KV heads. Moving the slider changes
  // the width of W_K and W_V, so the model itself changes size: 7.80B at MQA,
  // 8.84B at full MHA. The input embedding, 128256 x 4096, is a lookup rather
  // than a matmul, so it is neither streamed nor counted as arithmetic.
  var EMBED = 128256 * DMODEL;
  var BASE = 8.03e9 - 2 * DMODEL * (8 * DH) * LAYERS - EMBED;
  function params(kv) { return BASE + 2 * DMODEL * (kv * DH) * LAYERS; }
  var BW = 3.35e12, FLOPS = 989e12, HBM = 80e9;
  var LENS = [1024, 2048, 4096, 8192, 16384, 32768], KVH = [1, 2, 4, 8, 16, 32];
  var X0 = 62, X1 = 700, Y0 = 190, YTOP = 24, BMAX = 256;

  function perStep(b, L, kv) {
    var P = params(kv);
    var wBytes = P * BYTES;
    var cBytes = b * L * 2 * LAYERS * kv * DH * BYTES;
    var flops = 2 * P * b + 4 * L * DMODEL * LAYERS * b;
    var tMem = (wBytes + cBytes) / BW, tCmp = flops / FLOPS;
    return { w: wBytes, c: cBytes, tMem: tMem, tCmp: tCmp,
             tps: b / Math.max(tMem, tCmp) };
  }

  function draw() {
    var b = +bR.value, L = LENS[+lR.value], kv = KVH[+kR.value];
    var cur = perStep(b, L, kv), s = '', i;
    var top = 0;
    for (i = 1; i <= BMAX; i++) { top = Math.max(top, perStep(i, L, kv).tps); }
    top = Math.max(top, 1) * 1.12;
    function px(v) { return X0 + (v - 1) / (BMAX - 1) * (X1 - X0); }
    function py(v) { return Y0 - v / top * (Y0 - YTOP); }
    for (i = 0; i <= 4; i++) {
      var g = top * i / 4;
      s += "<line class='grid' x1='" + X0 + "' y1='" + py(g).toFixed(1) + "' x2='" + X1 +
           "' y2='" + py(g).toFixed(1) + "'/><text class='tick' x='" + (X0 - 8) + "' y='" +
           (py(g) + 3).toFixed(1) + "' text-anchor='end'>" + Math.round(g) + "</text>";
    }
    var fitPts = [], ghost = [];
    for (i = 1; i <= BMAX; i++) {
      var st = perStep(i, L, kv), pt = px(i).toFixed(1) + ',' + py(st.tps).toFixed(1);
      if (st.w + st.c + EMBED * BYTES <= HBM) { fitPts.push(pt); } else { ghost.push(pt); }
    }
    if (ghost.length && fitPts.length) { ghost.unshift(fitPts[fitPts.length - 1]); }
    if (ghost.length) {
      s += "<polyline points='" + ghost.join(' ') + "' fill='none' stroke='#8C77BC' " +
           "stroke-width='2.4' stroke-opacity='0.35' stroke-dasharray='5 4'/>";
      s += "<text class='tick' x='" + X1 + "' y='" + (YTOP + 10) +
           "' text-anchor='end'>dashed: will not fit in 80 GB</text>";

    s += "<polyline points='" + fitPts.join(' ') + "' fill='none' stroke='#8C77BC' stroke-width='2.4'/>";
    s += "<circle cx='" + px(b).toFixed(1) + "' cy='" + py(cur.tps).toFixed(1) +
         "' r='5' fill='#A8443E' stroke='#FFFFFF' stroke-width='1.6'/>";
    s += "<text class='axlabel' x='" + X0 + "' y='" + (Y0 + 22) + "'>batch size &#8594;</text>";
    s += "<text class='axlabel' x='" + (X0 - 8) + "' y='" + (YTOP - 8) +
         "' text-anchor='end'>tokens/s, all sequences</text>";
    var tot = cur.w + cur.c, BY = 236, W = X1 - X0;
    s += "<rect x='" + X0 + "' y='" + BY + "' width='" + (W * cur.w / tot).toFixed(1) +
         "' height='26' rx='3' fill='#3E6491' fill-opacity='0.85'/>";
    s += "<rect x='" + (X0 + W * cur.w / tot).toFixed(1) + "' y='" + BY + "' width='" +
         (W * cur.c / tot).toFixed(1) + "' height='26' rx='3' fill='#8C77BC' fill-opacity='0.85'/>";
    s += "<text class='axlabel' x='" + X0 + "' y='" + (BY - 7) + "'>bytes moved per decode step: " +

    s += "<text class='wnum' x='" + (X0 + 8) + "' y='" + (BY + 17) + "' fill='#FFFFFF'>" +

nobody knows how long a request runs, so systems reserved each its maximum
length. What that costs on real traffic is why vLLM exists.

One last cost differs in kind. Paging and batching leave a given model's
output untouched; evicting old tokens or storing them in four bits does not.
Sharing key-value heads is a third thing — not an approximation of a model but
a different model, trained to be one.


## 4. The Same Answer to Fifteen Decimal Places

Decoding 320 tokens through one attention layer, $d = 768$ in 12 heads, each
step done both ways, the largest disagreement is $2.2
\times 10^{-15}$ — float64 noise. The cache is *algebraically* exact: it
changes no term in the definition of attention. Two bf16 kernels will still
disagree in the last bits, but that is floating point, not the cache.

The saving has the shape the arithmetic claims. A cached step projects one
token and attends over $t$ rows: $8d^2 + 4td$. A recomputing step projects $t$
tokens and attends over $t \times t$: $8td^2 + 4t^2d$. Every term of the second
carries a factor $t$ the first does not, so the ratio is exactly $t$ — against
this dense baseline; one exploiting the mask tends toward $t/2$.

## 5. Chat This Over With Friends

A language model remembers nothing between words. Every token it writes is a
fresh call on the whole conversation so far, and if it truly started over each
time, the cost of a reply would grow with the *square* of its length. The KV
cache is the fix, and it is embarrassingly simple: each token's key and value
are computed once and kept, because a causal model can never go back and
change them. Notice what is not kept — the queries. A past token's key is
consulted forever; its question was asked once and never again. In a 70B model each
token costs 320 KiB of it, so a long conversation quietly accumulates 40 GiB,
for one user.

The version people repeat is that the KV cache is a decoder-only trick. Close,
but the reason is not the name of the block: encoder–decoder models cache
cross-attention keys quite happily, bidirectional though that is, while an
encoder caches nothing because appending a word rewrites every representation
it had. A row is keepable when nothing arriving later can change it. The fair
objection is that calling the cache *the* bottleneck overstates it — at a
large batch and a short context the weights still dominate — so the honest
claim is narrower: it binds at long context, which is where everyone now
operates. What is unsettled is the next move, since evicting tokens and
four-bit storage both change what the model computes, and stop being free in
the way paging was.
